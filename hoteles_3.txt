Plan de desarrollo en 10 fases para /hoteles
Fase 1 — Redefinir producto y congelar dirección

Objetivo: dejar por escrito que /hoteles ya no es “inteligencia hotelera B2B”, sino:

/hoteles = comparador y tracker diario de precios hoteleros por zona, fechas y condiciones de estancia.

Qué debe hacer Codex:

Crear:

docs/specs/hotels-product-direction.md

Debe explicar:

Qué será /hoteles.
Qué NO será.
Qué piezas actuales se conservan.
Qué piezas se renombran.
Flujo principal de usuario.
Modelo de datos objetivo.
Qué pasa con comp sets.
Qué pasa con paridad.
Qué pasa con Makcorps.
Plan de migración.

Criterio de aceptación:

No toca backend.
No toca frontend.
Solo documentación.
Queda claro que la prioridad es búsqueda por zona + tracking diario de precio.

Prompt para Codex:

Reorienta conceptualmente el módulo /hoteles.

La intención real de /hoteles es crear un comparador y tracker diario de precios hoteleros tipo Trivago.

El usuario debe poder buscar hoteles cerca de un área específica, con fechas, huéspedes y filtros básicos. La app muestra hoteles comparables por precio, proveedor y distancia. El usuario puede guardar una oferta o precio concreto para que Viru lo trackee cada día, igual que /watchlist hace con vuelos.

Crea docs/specs/hotels-product-direction.md.

No implementes código todavía.
No borres lo existente.
No toques backend/frontend.

Criterio de aceptación:

Cada seguimiento pertenece a un usuario.
No se rompe HotelWatchlistItem todavía.

Prompt para Codex:

Añade el modelo HotelTrackedOffer para convertir /hoteles en un tracker real de precios hoteleros.

Fase 3 — Separar “oferta actual” de “snapshot histórico”

Objetivo: que Viru pueda distinguir entre:

precio encontrado ahora;
precio guardado;
precio capturado cada día.

HotelRateSnapshot ya existe y es útil, pero debe conectarse mejor con HotelTrackedOffer.

Cambios recomendados:

Añadir a HotelRateSnapshot:

tracked_offer_id nullable
provider_run_id nullable
availability_status
deep_link nullable

Reglas:

Si el snapshot viene de una búsqueda normal, puede no tener tracked_offer_id.
Si viene de una revisión diaria, debe tener tracked_offer_id.
Mantener compatibilidad con snapshots antiguos.

Criterio de aceptación:

Los snapshots históricos pueden asociarse a un seguimiento.
El histórico de un tracked offer se puede consultar sin mezclarlo con otros hoteles/fechas.

Endpoint nuevo:

GET /api/v1/hotels/tracked-offers/{tracked_offer_id}/snapshots

Prompt para Codex:

Evoluciona HotelRateSnapshot para soportar tracking diario de HotelTrackedOffer.

Añade campos:
- tracked_offer_id nullable
- provider_run_id nullable
- availability_status
- deep_link nullable

Implementa endpoint:
GET /api/v1/hotels/tracked-offers/{tracked_offer_id}/snapshots

Mantén compatibilidad con snapshots existentes.
Añade tests de migración, creación y consulta por tracked_offer_id.

Fase 8 — Revisión diaria real de tracked offers

Objetivo: que los sweeps dejen de revisar “hoteles en general” y pasen a revisar ofertas trackeadas concretas.

Nuevo comportamiento de run_hotel_sweep:

Buscar HotelTrackedOffer activos.
Para cada tracked offer:
consultar provider con mismas condiciones;
guardar nuevo snapshot;
actualizar current_price;
calcular delta contra initial_price y snapshot anterior;
crear eventos si hay cambios relevantes.
Registrar HotelProviderRun.

Criterio de aceptación:

Un seguimiento activo recibe snapshots nuevos.
Se actualiza current_price.
Se puede ver evolución diaria.
No se mezclan fechas distintas.

Prompt para Codex:

Reorienta run_hotel_sweep para revisar HotelTrackedOffer activos.

Nuevo flujo:
1. Listar HotelTrackedOffer activos.
2. Consultar provider con las mismas condiciones guardadas.
3. Crear HotelRateSnapshot asociado a tracked_offer_id.
4. Actualizar current_price.
5. Crear eventos de cambio si aplica.
6. Registrar HotelProviderRun.

Mantén compatibilidad con mock provider.
Añade tests de sweep con tracked offers.

provider_changed
availability_returned

Criterio de aceptación:

Alertas se crean desde un tracked offer, no solo desde hotel.
El usuario no ve nombres técnicos.
Eventos se muestran como “Cambios detectados”.

Prompt para Codex:

UI visible:

- Avísame si baja más de X %
- Avísame si sube más de X %

No mostrar “alert rules” ni “parity_break” como lenguaje principal.

Internamente puedes mantener HotelAlertRule/Event si conviene, pero deben asociarse a tracked_offer_id cuando aplique.
